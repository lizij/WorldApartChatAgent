- **记忆形态重构（2026-10-16，真实数据实测）**：原 memory.md 退化成"事件日记/流水账"——根因是
  旧 prompt 只规定"保留什么"、没规定"记忆长什么样"，输入本身又是带时间戳的对话流水，且"合并旧记忆"
  会**风格自我强化**。已改为**状态型六分区模板**（【身份与称呼】【当前关系】【未了之事】【赠予往来】
  【习惯与忌讳】【玩家所述，未经证实】），强制现在时陈述状态、禁用"当夜/第二次后/随后"等过程口径、
  要求忽略旧记忆文体重排。用真实玩家数据实测：旧 ~490 字 8 条流水 → 新 ~456 字 6 分区，
  过程口径清零、保留"未经证实"标注，并新增高价值的「习惯与忌讳」条目。
  与超限重试配合（六分区不得整节删除，只压每条字数）；现有 memory.md 会在下次摘要（含空闲兜底）
  时被自然重排，无需手工改。

- **重写格式校验误判修复（2026-10-20，0.6.2）**：真机出现
  `rewrite_failed:module3:rewrite_output_format_changed`。原因：游戏把「最高优先级规则」
  排在 `## 输出格式` 标题之下（与 JSON 结构同节），旧校验比较整节文本；重写模型删掉这条
  规则后节文本改变 → 整模块被回退，规则反而原样保留。
  修复：只比较 `## 输出格式` 内第一个**配平的 JSON 对象**（字段名、枚举、层级逐字一致），
  标题下的说明文字允许被删改；极少数没有 JSON 结构可锚定的模块才退回整节比较。
  同时失败模块保留**模型草稿**供详情查看，并统一日志与详情里的模块编号（`id` + 消息 `index`）。

- **重写格式枚举漏值修复（2026-10-20，0.6.3）**：真机出现

  重写失败原因 11、日志类型 11（新增 `idle_flush` / `memory_write` 徽章色）、状态 5；
  另对自由文本 error 做前缀/HTTP 状态码映射（`fetch failed`→连不上上游、
  `上游 401`→API Key 无效或已过期…）。**未登记的码自动退化为只显示原码**，不会空白。
  顺带给 `idle_flush` / `memory_write` / `auth` / 通用分支补了更可读的正文
  （空闲补压显示「已聊 N 轮 / 上次压到第 M 轮 / 已空闲 X 分钟」）。
  用真实日志里出现过的全部 9 种 warning、11 种 rewrite 原因、11 种 kind、5 种 status 逐条断言通过。

- **记忆「每轮都报超限」修复（2026-10-27，0.15.2，真实数据实测）**：0.15.1 上线后日志里
  每轮都是 `memory_over_limit:5136>5000`（`releases/data/logs` 统计 6/6 次超限），玩家看到
  「记忆超出上限，已截断」。逐层定位到四个原因：
  ① **软目标与硬上限用了同一个数**（都是 5000），模型把上限当下限，自然产出 5010~5358；
  ② **真正的绑定约束是 `max_tokens`**：模型会把输出额度用满，`maxTokens=4000` 时实测出现
     `finish=length`，正文被从中间切断（标定实验：软目标 4600/4400/4200/4000 分别产出
     5235/5245/5193/5219 字，其中前两组 `finish=length`）——**调软目标对产出长度几乎无效**；
  ③ **prompt 自相矛盾**：规则第 10 条写「不许因为重写就把信息丢掉」，而【已有记忆】本身已 4997 字，
     模型因此在物理上无法压缩；
  ④ **兜底是「砍尾」**：`slice(0, limit)` 会把【同场】【习惯与忌讳】整段丢掉。
  修复：软目标改为硬上限的 96%；调用额度改为 `max(maxTokens, ceil(上限×1.15/1.4))` 保证能写完；
  prompt 第 10 条改为「字数优先，允许合并/压缩旧条目，只死保身份·关系·未了之事」；重试指令
  明确「至少减掉 N 字」并授权精简低优先级分区，且只接受「明显变短」（<上次-40）的结果；
  兜底换成新增的 `fitMemorySections()`——**七个分区全部保留**，每次从「最长且高于保底」的分区
  按行裁，只裁刚好需要的字数。**稳态小幅压缩不再算告警**（`fitted:true` + 中性标签
  「已按板块压缩 N 字」），只有砍掉 >8% 才记 `memory_over_limit`。
  实测 4 轮连续摘要（每轮喂 40 条真实对话，`maxMemoryChars=5000`）：
  修复前 4/4 轮全部告警；修复后 **4/4 轮无告警**，记忆稳定在 4893~4964 字，七个分区齐全，
  省略标记仅 1 处。`fitMemorySections` 边界测试：4949 字在 5000/4900/4600/4000/3000/2000/300
  上限下分别压到 4949/4863/4509/3974/2944/1968/298，分区始终 7/7；旧六分区格式与极小上限均正常。

- **端口占用自动顺延 + 上游超时可配（2026-10-28，0.16.0）**：
  ① **端口顺延**：工坊反馈「显示端口 8790 已被占用」。`src/app.js` 的 `listen()` 改为
  逐个尝试 `want … want+19`（`PORT_FALLBACK_TRIES=20`，即 8790–8809），只对
  `EADDRINUSE` 顺延，其他绑定错误（如 `EADDRNOTAVAIL`）照旧抛出；
  换端口后 `config.update({server:{port}})` 写回 `config.json`，并记
  `kind:"server", status:"port_fallback", from, to`。
  `/api/status` 新增 `port` 与 `portFallback`（仅当**本次启动**真的顺延过才有值），
  管理页概览据此区分两种情形：本次自动顺延 → 黄字强提醒「请把游戏 Base URL 改成 …」；
  玩家自己在 config 里改过端口 → 中性提示「当前使用非默认端口 N，游戏 Base URL 需一致」，
  不会误报成「自动切换过」。执行日志把该记录翻成中文（`port_fallback → 端口已自动切换`）。
  CLI 横幅与 Electron 窗口本就取 `start()` 返回值，无需改。
  实测（假数据目录、临时端口）：占 18910+18911 → 起 18912 且 `config.json`、`/api/status.baseUrl`
  同步、重启仍 18912；占满 20 个 → 抛 `EADDRINUSE`（`portRange=[18930,18949]`）且**不改配置**；
  绑定不可用地址 → `EADDRNOTAVAIL` 直抛、不顺延。真机场景实测：8790 被占用时起在 8791，
  管理页提示条（黄字强提醒）与日志条目（绿色「端口已切换」徽章）均正确，浏览器控制台无报错；
  重启后 `portFallback` 归 `null`，概览改为中性提示「当前使用非默认端口 N」，
  不会把玩家自己改的端口误报成自动切换。
  **打包 exe 实测**（`--test` 档，临时目录）：8790 空闲 → 起 8790、`portFallback=null`（无顺延记录）；
  8790 被占用 → 起 8791，概览黄字强提醒，执行日志两条绿色「端口已切换」记录，
  重启后 `config.json` 的 8791 被沿用（`portFallback` 归 null、概览转为中性提示）；
  再占 8791 → 顺延到 8792 并写回配置。exe 内 `resources/public` 为最新页面。
  ② **上游超时进界面**：后端早有 `upstream.connectTimeoutMs`（15000）/`requestTimeoutMs`
  （300000，兼流式空闲超时），`PUT /api/config` 也已校验接收，只是管理页没暴露。
  在「上游 Provider」卡片加两个毫秒输入（默认 15000 / 300000），保存走现有 `saveUpstream`。
  实测：回填 15000/300000，填 30000/600000 保存后 `/api/config` 回读一致。

## 排障

- 记忆读起来像流水账 / 事件不消失：原 prompt 只规定"保留什么"、没规定"记忆长什么样"，
  且输入本身是带时间戳的对话流水，再叠加"合并旧记忆"造成的**风格自我强化**，就会退化成日记体。
  已改为状态型六分区模板（见 [memory-rules.md](memory-rules.md)）。若仍出现过程口径，检查是否改动了 SYSTEM_PROMPT。

- **记忆体量与超限压缩（2026-10-16 实测）**：4 组对照测出中文约 **1.4 汉字/token**（多组比值 1.39~1.40），
  故 `maxMemoryChars` 的有效上限 ≈ `maxTokens × 1.4`；且 **prompt 里的「字数上限」几乎不被遵守**
  （上限 800 时输出 1153 字，加"硬约束+优先级"仍 1077 字，仅少 76）；模型自然产出稳定在
  **780~1187 字，与上限设 800 还是 3000 基本无关**。→ 结论：**调大 `maxMemoryChars` 不会让记忆变长**，
  只会让摘要每次都触发截断。据此把默认改为「上限 3000 / maxTokens 2500」（匹配），
  `injectMaxChars` 同步提到 3200，并新增**超限重试**：同一段生成 1187 字、上限 600 时，
  开启重试 → `retries=2`、最终 501 字且句子完整（内容由模型主动取舍）；不重试 → 只能按行切尾部 569 字。
  默认配置下（上限 3000 vs 自然 ~1150 字）截断与重试基本都不会触发。

- 记忆写不长 / 每次都超限：先查 `maxMemoryChars` 是否远超 `maxTokens × 1.4`（中文 1.4 汉字/token）。
  上限设得比模型能写的还大，不会让记忆变长，只会让每次摘要都触发截断。
  另可看日志 `kind:"summary"` 的 `generatedChars` / `retries` / `truncated`。

- 记忆"少记了最后几句"：检查是否只有水位触发（`everyTurns=4`）而没有空闲兜底——
  确认 `memory.summarizer.idleFlushEnabled=true`；`state.turns > lastSummaryTurn` 的 NPC 在空闲
  `idleFlushMs` 后会被自动补压，日志 `kind:"idle_flush"` + `kind:"summary" reason:"idle"`。
- 401：游戏 Key 与当期档位的 `server.apiKey` 不一致（页面顶部可复制；注意正式档与测试档 Key 不同）。
- 同一个 NPC 出现两个档案（"她好像忘了我刚才说的话"）：多半是 mod 改了全名导致分流。
  按 [memory-rules.md](memory-rules.md) 的「mod 全名 → 原名」校正即可；已有档案可停服后把目录改名并同步 `state.json` 的
  `slug`/`sessionId`（sessionId = `ses_` + `sha256("npc:"+新slug)` 前 24 位）。
- 503：在页面填写上游 API Key。
- 回复为空：多数是上游 `max_tokens` 偏小——开启思考时会先耗 reasoning 额度再产出正文。
  游戏请求给的是 4000（正常）；若某个调用方给得很小，才考虑对那一侧禁用思考。
- 响应变慢（约 3~5s）：这是**默认行为**（不干涉思考，模型在推理），不是故障。要更快就开
  `upstream.disableThinking`，但要接受规则遵从度下降。
- 首字延迟突然明显增加：先查是否开启了「请求重写」（`requestRewrite.enabled`）——它会先多跑
  一次完整的 system 改写；关闭后即恢复。若游戏端请求超时较短，不建议开启。
- 端口占用：程序会**自动顺延**到下一个空闲端口（8790–8809），把实际端口写回当期档位的
  `config.json`，并在管理页概览提示。此时必须把游戏 Base URL 改成提示里的新端口，
  否则游戏连不上。若 20 个端口全被占用，会报「8790–8809 均被占用」，需要先关掉占用者。
  注意换过端口后不会自动切回 8790。
- 数据"不见了"：先确认是哪个档位——正式档 `data/`，带 `--test` 启动时是 `data_test/`（页面「数据目录」一栏可确认）。
