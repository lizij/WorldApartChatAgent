# 多 NPC 共演 · 方案评估

> 状态：**已实现（0.9.0），待真机验收**。
> 目标版本：`0.9.0`（新增管理页配置项，MINOR）；实际交付时按
> [contributing.md](contributing.md) §1 递增 `package.json` 的 `version`。
> 定位：**【实验性】**，默认关闭，开启后产生**额外 token 消耗**。

## 0. 代价声明（已知并接受）

| 代价 | 数值 | 出现条件 |
| --- | --- | --- |
| 额外 token | 约 +2.3k tokens / 轮 | 仅本轮有配角开口 |
| A 侧额外输入 | 约 +300~400 字 | 配角在场即发生 |
| 首字延迟 | +1~2s | 仅玩家点名 B（B 必须先跑完，A 才能观测） |
| 尾句延迟 | +0.6~1.8s | 仅 A 先说话、B 随后接话（尾部插槽） |
| 叠加请求重写 | 每轮 +1 次预处理调用，约 5k~8k 字 | 同时开启 `requestRewrite` 时 |

以上是**设计上的固有成本**，不是待优化项：B 若要有独立设定与记忆，就必须独立请求；A 若要真实观测 B，就必须等 B 先说完。产品层用【实验性】【额外 token 消耗】标注并默认关闭来管理这个代价。

## 1. 需求摘要

游戏设定里每个 NPC 只能单独对话，但 NPC 之间在人物、关系、场景上彼此交叉：

- 与 NPC A 聊到 NPC B 时，A 常常表现为“不知道 B”或失忆；
- 无法实现 A、B 同场对话或共同演出；
- 同一批 NPC 的记忆各自隔离，玩家体验割裂。

目标能力（对应原始需求编号）：

| 编号 | 需求 | 本方案落点 |
| --- | --- | --- |
| 3.1 | 全局开关，默认不启用 | `multiNpc.enabled=false` |
| 3.2 | 单人对话即二人戏，玩家兼导演/编剧，用括号指定事实与演出要求 | 括号指令解析 + 共演块声明 |
| 3.3 | 提及 B 时检查 B 是否在记忆库；在库则由括号指引入场/离场 | 在场状态机 + **A 侧即时认识判定**（不建全局名录） |
| 3.4 | B 入场后变多人对话；不指定角色默认对 A；括号点名则对 B；全员共享记录 | 轮内编排 + 寻址判定 + 公共观测账本 |
| 3.5 | 模拟配角系统，最小 token，**可单独请求上游**；输出括号动作 + 台词 | 角色卡确定性抽取 + 配角独立请求（主线） |
| 3.6 | 配角是否写入记忆，默认不启用，提供开关 | `multiNpc.coStarWritesMemory=false` |
| 3.7 | 每个 NPC 单独设置“是否支持共演”，默认不启用；未启用的 NPC 不会被邀请 | `data/npcs/<slug>/cast.json={enabled:false}` + 名册门禁 |
| 3.8 | 显式调试指令 `/invite XXX`、`/remove XXX` | 指令解析（优先于括号）+ 文本剥离 |

## 2. 现状调研（基于 `releases/data` 真实数据）

### 2.1 数据规模

| 项目 | 实测 |
| --- | --- |
| NPC 档案 | 17 个（`data/npcs/<slug>/`） |
| 长期记忆正文 | 平均 724 字，最长 2976 字（江楚弦），最短 188 字 |
| 玩家发言 | 840 条，其中 **491 条（58%）含括号叙述或【】指令** |
| 单轮 NPC 请求 | 最近一次真实请求：38 条消息、11,905 字、**8,165 tokens**（上游精确 usage） |
| 请求体来源分布 | 游戏 system 3,066 + 1,858 字、history 2,894 字、外置记忆 3,278 字、外置提示词 685 字、格式提醒 65 字 |

### 2.2 可直接复用的角色卡字段

真实 system 的章节结构稳定，`intake/` 存档里可直接抽取：

| 章节 | 字数范围 | 用途 |
| --- | --- | --- |
| `## 角色设定` | 5~18 字 | 确定姓名 |
| `## 角色背景` | 64~266 字 | 身份、居所、亲缘关系 |
| `## 说话习惯` | 36~450 字（部分 NPC 无此节） | 口吻、自称、口癖 |
| `## 角色属性` | 308~434 字 | 性格、外貌、善恶 |
| `## 守住世界观` | 188~381 字 | 公共世界观约束 |
| `## 通用要求` | 768~1204 字 | 行为通则（可精选后复用） |

结论：**配角角色卡可以用纯正则确定性抽取（约 500~1100 字），不需要额外模型调用**，这是“最小 token”方案的基础。

### 2.3 跨角色关系现状

17 个 NPC 中 13 个在设定或记忆里提到过其他 NPC，例如：

- 纪澜之 ↔ 纪小蝶 / 纪小花（母女、姐妹）；
- 江楚弦 ↔ 章籽梦（同在一间杂货铺，江楚弦帮工）；
- 李清月 ↔ 宓青苓 / 程砺（玄一门）；苗烬 ↔ 赤遥（宗门）。

但**关系是不对称的**：江楚弦的设定里提到章籽梦，章籽梦的记忆里却完全没有江楚弦。这正是玩家感到“NPC 失忆”的直接来源。

> 决策：**不建全局名录**。NPC 虽多但关系简单（亲属、朋友为主），维护一份跨 NPC 名录需要定期扫描与更新，成本高、对共演效果提升有限。改为 B 入场时**即时判定 A 是否认识 B**（扫 A 自己的记忆与当轮 system，一次字符串匹配，零维护），并在共演块里按“认识 / 不认识”写不同的措辞。

### 2.4 协议事实

- **游戏只在玩家发言时发一次请求**，没有“玩家不说话的下一轮”。因此一轮必然由玩家指令开始，也必然在 A 的这次请求内收束——这直接决定 §5.0 的轮次模型。
- 游戏把上一轮回复的**原始 JSON 字符串**作为 `assistant` 消息回传，因此 B 的台词一旦写进 A 的 `content`，下一轮会自然进入 A 的上下文。
- 但游戏 history 可能被裁剪，且 B 的台词被包在 A 的 JSON 里；B 的请求需要干净的多说话人记录，必须用本工具自己的账本重建（见 §5.6、§5.8）。
- 真实 system 是 CRLF 文本、拆成多条、与历史消息交错（详见 [AGENTS.md](../AGENTS.md) §4）。
- 识别、注入与转发链路见 [src/server.js](../src/server.js)、[src/identify.js](../src/identify.js)、[src/memory/inject.js](../src/memory/inject.js)。

## 3. 硬约束（先于方案成立）

1. **一次请求只能返回一个 JSON、一个角色气泡。**
   B 的台词只能作为文本写进 A 的 `content`；头像、表情、TTS 与全部游戏机制字段（`emotion`、`control`、`intent`）**只属于 A**。B 本身不产出这些字段，因此 B 不参与任何游戏结算——这是设计结果，不是缺陷。
2. **真流式红线（插入的准确位置）**
   [contributing.md](contributing.md) §2 第 8 条要求上游转发“原样直通、不缓冲”。共演模式必须**只在 `content` 字符串值内部插入**，不能把文字拼在 JSON 外层：

   - 上游 SSE 的 `delta.content` 是**整段回复文本**（即 `{"content":"…","emotion":"…"}` 这段 JSON 的字符流），不是解析后的字段值。因此：
     - **B 先说话**：在 `"content":"` 之后、A 的第一个正文之前插入 B 的**JSON 转义后**台词；
     - **A 先说话**：在 `content` 字符串的**闭合引号之前**插入 B 的转义台词。
   - 两处都需要一个**流式 JSON 扫描器**：跟踪字符串/转义状态，定位第一个顶层 `"content"` 字段的起止。插入点在 A 的回复开头或结尾，因此缓冲只涉及 1 个 delta（≤256 字节）；A 先说话时若 B 未就绪，最多把尾部这 1 个 delta 延迟 1.5s。
   - 注入方式可以“拆分该 delta”，也可以补一个**合成 chunk**（必须复制上游 chunk 的 `model/id/object/created` 等信封字段，只替换 `choices[0].delta.content`，`finish_reason=null`）。
   - 定位失败（回复不是预期 JSON 结构）时：**B 先说话 → 整轮作废**（A 已经观测到 B，不能只显示 A）；**A 先说话 → 丢弃 B 的台词**（A 从未看到 B，不会产生矛盾），日志记 `costar_slot_missed`。

   仍需在 [contributing.md](contributing.md) §2 第 8 条补一句作用域限定（仅共演模式、仅上述两处、失败回退原文）。
3. **B 不产生游戏结算，只产生文本。**
   - B 只输出“括号动作 + 台词”，没有 `emotion/control/intent/gift_item`，因此不会触发好感、关系、交易或赠物结算；
   - 玩家对 B 的“行为”也只是文本（游戏没有 B 的交互入口），不存在对 B 的送礼或建立关系；
   - 因此唯一要守的是**文本一致性**：B 不得声称赠出/收下物品、不得宣称关系已建立或任务已完成、不得输出 `{GIFT}` 占位符——这些在游戏里没有对应结算，写出来就是“说了却不存在”的假事实。
4. **记忆污染。**
   B 的台词会进入 A 的 `conversations.jsonl`，现有摘要器按“玩家 / NPC”两方渲染，会把 B 的言行记成 A 的。必须结构化区分说话人，否则几轮后 A 的人设会漂移。

## 4. 方案对比

| 维度 | A. 单调用·多声部 | B. 独立配角请求 + A 原文回声 | C. 独立配角请求 + 观测注入（推荐） |
| --- | --- | --- | --- |
| B 的生成 | 同一模型在 A 的 system 内同时扮演 A/B | B 先独立请求，再要求 A 逐字引用 | B 与 A 各自独立请求；先说话者先流式，后说话者的台词插在尾部 |
| 首字延迟 | 不变 | **+0.6~1.5s** | A 先说话：A 不变；玩家点名 B：**+1~2s**（B 先跑完，A 才发请求） |
| 额外 token | A 侧 +约 1.2k~1.5k 字 | B 调用约 3.1k 字 ≈ 2.3k tokens + A 侧观测块 | 同 B（B 调用约 2.3k tokens + A 侧观测块约 300 字） |
| B 保真度 | 中（可能串味） | 高 | 高 |
| 信息隔离 | 差（A 可看到 B 私密记忆） | 好 | 好（A 只看到 B 的公开输出） |
| 显示可靠性 | **保证** | 依赖逐字回声（预期 85%~95%） | **保证**（系统插入） |
| 流式合规 | 完全合规 | 完全合规 | 仅插入点局部缓冲（≤1 个 delta），需补红线作用域 |
| 实现复杂度 | 低 | 中 | 中（调用编排 + JSON 转义 + 尾部插槽 + 失败回退） |

补充折中方案 **B′ 预演模式**：B 独立请求只生成“演出提示”，不要求逐字显示，由 A 写出完整场景。满足“单独请求”，不改流式，但多一次延迟，且 A 可能改写 B 的语义。

### 推荐结论

- **主线采用方案 C**：B 的设定、记忆、提示词从不进入 A 的请求，B 走独立调用；A 只观测 B 的公开输出（台词/动作/表情）。这直接对应“B 更像真人、A/B 数据隔离”的目标。
- **方案 A 不作为任何运行期降级**：B 调用失败时**不允许 A 现场代演 B**（那是旧方案的思路，容易写出与 B 设定完全不符的内容）；B 先跑失败则整轮作废，A 先说完则 B 缺席。
- 方案 B（要求 A 逐字回声）同时付出延迟与回声不可靠两项成本，**不做**。
- “先说话者先生成”是唯一的排序原则：谁被玩家点名，谁先跑；需要另一方反应时，串行加一轮（见 §5.0）。

### 4.1 “A 的感知”与“A 代演 B”是两个问题

玩家直接面向 B 说话时，输出仍必须由 A 的请求产生。这容易被读成“A 必须知道我在跟 B 说话，还得替 B 说话”，但二者性质不同：

| 问题 | 是否真的奇怪 | 结论 |
| --- | --- | --- |
| **感知**：A 知道玩家转向 B 说话 | 不奇怪 | 三人同场时，旁观者本来就知道。只要不写成“请转述”，而是写成现场事实，A 只是在场者 |
| **代演**：A 写出 B 的台词 | 奇怪 | 会串味、会替 B 表态，也让 `emotion/control` 归属混乱。应把生成权交给 B |

**感知层的写法约束**（消除“传声筒”感）：

- 共演块只陈述事实：“章籽梦此刻在场；玩家转向她开口。”不写“请转述”“请代她回答”。
- 明确 A 的合法反应只有三类：极短在旁反应（一个动作/半句）、自己也插一句、不接话。
- 玩家点名 B 时，默认**不要求 A 回应内容**，避免 A 复述玩家对 B 说的话。

**代演层的解决方式**（主线）：

- B 走独立请求，A 的 prompt 里**没有 B 的设定、记忆、提示词**，只有“B 在场”与“B 这一轮说了/做了什么”这类公开观测。
- 台词插入由系统完成，不需要模型配合输出占位符：
  - **B 先说话**：B 跑完后再发 A 的请求，B 的台词插入 A 回复里 `"content":"` 之后、正文之前（缓冲仅 1 个 delta）；
  - **A 先说话**：A 正常流式，B 的台词插在 `content` 字符串闭合引号前（最多把尾部 1 个 delta 延迟 1.5s）。
- **B 先跑时失败/超时** → **整轮作废**：不发 A 的请求，游戏端收到错误，A/B 都不落盘（避免后续记忆错乱）。
- **A 已先说、B 接话失败** → A 的回复原样成立；**不注入“B 没接话”之类的任何文字**，也不写进 A 的观测块与账本叙事，下轮自然继续。日志只在内部记 `costar_failed`。
- 顺序：谁被点名谁先开口；需要对方反应时串行加一轮（见 §5.0）。

**产品层两个规避手段**（按侵入性排序）：

1. **剧本化输出（推荐）**：B 在场时整段统一为 `名字：台词` 分行，包括 A 自己。玩家读的是“一场戏”，消解“A 的气泡里为什么有别人”的错位感。
2. **A 静默 + 私下交谈**：玩家写 `（拉章籽梦到一旁低声说）`，A 的 `content` 只留“在柜台后拨算盘，没听清”，主体由 B 承担；同时满足“不想让 A 听见”的需求。

> 决策：**不做“跨窗口共享舞台”**。它需要玩家在游戏里手动切换对话对象，且两边的游戏状态各自独立，收益不抵复杂度。

两者可共存：共享 transcript 本来就是共演底座；“剧本化”与“A 静默”只是输出契约的两种取值。

## 5. 推荐方案详细设计

### 5.0 玩家视角的期望效果（轮次模型）

把聊天窗口理解成一个**指令 + 公共观测区**：

- 玩家说一句 = 给一条指令；被指定的 NPC 各产出一次结果；玩家的话与所有 NPC 的结果都进入同一个窗口，成为下一轮的公共观测。
- 单人时就是默认二人戏：一问一答，一一对应，玩家先说。
- 多人时保持同一条规则：**一轮之内，被点名的每个角色最多产出一次**；没被点名的角色可以只给一个在旁反应（动作/表情/沉默），也可以完全不说话。

“一轮”= 游戏发来的一次请求。因为游戏只在玩家发言时才发请求，所以一轮必定由玩家的指令开始。

#### 5.0.1 六种情形与调用顺序

| 玩家本轮的意图 | 谁先跑 | 谁后跑 | 调用数 | 玩家看到的顺序 |
| --- | --- | --- | --- | --- |
| 只对 A（默认） | A | — | 1 | A |
| 对 A，且括号里给 B 一个动作/指名 B 接话 | A | B（看到 A 的输出） | 2（串行） | A → B |
| 只对 B | B | A（看到 B 的输出） | 2（串行） | B → A |
| 同时对 A、B | 正文里先被点名者；不明确则 A | 另一方（看到前者的输出） | 2（串行） | 前者 → 后者 |
| A 对 B 说话（玩家指令 A 去问 B） | A | B（看到 A 的输出） | 2（串行） | A → B |
| B 对 A 说话（B 先开口并问到 A） | B | A（看到 B 的输出） | 2（串行） | B → A |

排序原则只有一条：**先说话者先生成，后说话者看到前者的公开输出再生成**。这样每一方都对上一句有真实反应，不需要 AI 现场编造对方的台词。

排序兜底：玩家同时点了两个名字、又不是“同时应答”的语境时，**默认 A 先开口**（与游戏默认视角一致），B 随后接；只有括号里先出现 B、或明确“B 先说”时才 B 先。

延迟代价：被点名的是 A 时，A 仍然第一个开跑，首字延迟不变；被点名的是 B 时，B 必须先跑完（禁用思考，约 0.6~1.8s），A 才发请求，首字延迟约 +1~2s。这是“A 必须真实观测到 B”的必然成本，已计入 §0。

#### 5.0.2 最难的一块：A 与 B 互相对话

这是本轮讨论暴露出的真正难点。候选做法：

| 做法 | 说明 | 评价 |
| --- | --- | --- |
| ① 串行链（推荐） | 先说话者生成 → 后说话者带着前者的公开台词生成 → 两句按时间顺序合并 | 每一轮最多 2 次**发言**调用，A/B 都有真实反应，不编造（请求重写另计） |
| ② 延后一轮 | 后者只在**下一轮**（玩家下一次发言）回应 | 省一次调用，但玩家会觉得对方“反应慢一轮”，只在超出调用预算时使用；上一轮内容已在 history 里，无需额外注入 |
| ③ 让 A 现场编 B 的话 | A 直接写出 B 的台词 | **不做**：极易写出与 B 的设定/记忆不符的内容，正是玩家担心的点 |

调用预算（`maxCallsPerTurn`，默认 2）用尽后的处理：

- A 问 B、B 答完后 A 还想再反应 → 第 3 次调用不做，留到**玩家下一次发言**时自然接上。**不需要额外注入“上一轮”提示**：上一轮的完整内容已经在游戏 history 与账本里，A 看得到；只记 `costar_deferred` 便于统计；
- 反之亦然。

#### 5.0.3 三条硬规则

1. **隔离**：B 的 `角色设定/角色背景/说话习惯/角色属性/记忆/prompt.json` 只进入 B 自己的请求；A 的请求里只有“B 在场”和“B 这一轮的公开输出”。
2. **只观测公开行为**：A 能看到 B 说了什么、做了什么表情动作，看不到 B 的心里活动与设定。B 同理，只能看到 A 的公开输出与本场公共记录。
3. **B 只有文本，没有机制**：B 不产出 `emotion/control/intent`，也拿不到 `gift_item`；玩家对 B 只能说话与叙述动作。因此 B 在文本里**不得声称赠物、交易、关系确立或任务完成**，也不得出现 `{GIFT}`——游戏里没有对应结算，写出来就是假事实。

### 5.1 数据流总览

```
游戏请求（NPC A，玩家一句指令 = 一轮）
  │
  ├─ ① 分类 / 识别（沿用 identify.js）
  ├─ ② 共演开关检查（关闭 → 原有链路，零影响）
  ├─ ③ 指令解析：入场 / 离场 / 点名 / 括号给 B 的动作（仅括号内）
  ├─ ④ 在场状态更新（data/npcs/<A>/stage.json）
  ├─ ⑤ 认识判定：A 的记忆/当轮 system 里是否出现过 B 的名字（决定共演块的措辞）
  ├─ ⑥ 轮内编排（先说话者先跑，最多 2 次发言调用；若开启请求重写，先做一次预处理，见 §5.11）：
  │     ├─ 被点名的是 B → 先跑 B（非流式）→ B 的公开输出写入 A 的观测块 → 再跑 A（流式）
  │     └─ 被点名的是 A → 先跑 A（流式）→ 需要 B 反应时再跑 B（非流式），插在 A 的 content 尾部
  ├─ ⑦ A 侧组装：记忆 → 提示词 → 共演观测块（在场角色 + 已发生的公开输出）→ 格式提醒 → user
  ├─ ⑧ 转发 A（真流式）：B 先说话则插入 `content` 开头；B 后说话则在 `content` 闭合引号前插入
  ├─ ⑨ 超出调用预算的反应：延后到下一轮（`costar_deferred`）
  └─ ⑩ 响应结束后异步：按插入元数据写 segments、落盘、摘要
       └─（可选）把 B 的段落写入 B 的 conversations.jsonl
```

### 5.2 配置（`config.json` 新增段）

```json
{
  "multiNpc": {
    "enabled": false,
    "maxCoStars": 1,
    "maxCallsPerTurn": 2,
    "speakPolicy": "addressed",
    "outputStyle": "script",
    "allowASilence": true,
    "coStarWritesMemory": false,
    "transcriptTurns": 8,
    "skipOnTask": true,
    "autoExitIdleMs": 7200000
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `enabled` | 总开关（需求 3.1），关闭时请求体与当前版本**逐字节一致** |
| `maxCoStars` | 同时在场配角上限，默认 1（本轮只验证 1 个） |
| `maxCallsPerTurn` | 一轮内最多几次 **NPC 发言调用**：`2`（默认，A+B 各一次）；`1` = 省 token 模式，只跑主角 A（玩家点名 B 时 B 不开口，日志记 `costar_skipped`）。请求重写属于预处理，不占这个额度 |
| `speakPolicy` | `addressed`：本轮被点名 / 新入场 / 括号里给了 B 动作才开口；`always`：在场每轮都接 |
| `outputStyle` | `script`：多人场景统一 `名字：台词`（含 A 自己）；`inherit`：保持 A 的第一人称。默认 `script` |
| `allowASilence` | 允许 A 在被点名的是 B 时只给极短在旁反应 / 不接话。默认开 |
| `coStarWritesMemory` | 需求 3.6，默认关 |
| `transcriptTurns` | 传给配角的共享对话条数 |
| `skipOnTask` | 只在**真任务/话题轮**退化单人戏：存在 `## 本次话题` / `## 收尾判定`，或 `## 任务：X` 的标题不是“闲聊” |
| `autoExitIdleMs` | 超时自动清场（默认 **120 分钟**，管理页以“分钟”填写）：在场期间每轮成功回复都会刷新时间戳 |

管理页保存时沿用 [src/server.js](../src/server.js) 的 `intIn` / 布尔归一化，非法值忽略、数值夹取。

### 5.3 在场状态与指令解析（需求 3.3 / 3.4）

状态文件 `data/npcs/<A>/stage.json`：

```json
{
  "sceneKey": "杂货铺",
  "onStage": [{ "slug": "章籽梦", "name": "章籽梦", "since": "2026-10-20T01:00:00.000Z" }],
  "updatedAt": "2026-10-20T01:02:00.000Z"
}
```

**`sceneKey` 只取地点**（游戏 system 的 `**时间地点**` 里的第三段，如 `杂货铺`）。**绝不能把时间/时辰算进去**：真实数据里 `时辰` 会随对话推进而变，若 sceneKey 含时间，配角会每轮被清场。地点变化才代表“换场”。

**入场/离场只认括号内的显式指令**，避免误判（真实数据里 58% 的玩家消息含括号，且大量是动作叙述）：

| 语义 | 句式示例 | 匹配规则 |
| --- | --- | --- |
| 入场 | `（章籽梦走过来）`、`（章籽梦推门进来）`、`（章籽梦赶来）` | 已知名字 + 入场动词 |
| 离场 | `（章籽梦离开了）`、`（章籽梦告辞退下）` | 已知名字 + 离场动词 |
| 点名（括内） | `（对章籽梦说）`、`（看向章籽梦）`、`（问章籽梦）` | 指令词 + 已知名字 |
| 点名（正文） | `章籽梦，你怎么看`、`章籽梦你来了`、`章籽梦在吗` | **句首/分句首出现已知名字**，后接 `，`、`你/妳`、`在吗`、`呢`、问号等 |
| 仅提及 | `章籽梦最近怎么样` | **不触发入场**，也不注入任何提示（只按 A 自己的记忆/设定自然回应） |

点名判定细则（**这是最容易漏的部分**）：

- 顺序：**先按“点名”出现的先后**决定谁先开口；入场括号里的名字**不算点名**（`（章籽梦走进来）` 只是入场）；
- `章籽梦你来了` 这类“名字在句首、无括号”的直呼必须命中，否则玩家按示例写就拉不进 B；
- `章籽梦最近怎么样` 属于“向 A 提及 B”，不是点名——差别在于名字后是否直接接第二人称/问句；
- 名字末尾要处理中文边界（`章籽梦的铺子`、`章籽梦家` 不算点名；`章籽梦，` 算）。

其它入口约束：

- **直接点名一个不在场的 B → 自动入场**（玩家已经在对她说话，不能让她“不理人”），日志记 `cast_auto_enter`；同一轮若同时写了离场指令，以**离场**为准；
- **B 必须有可用的 intake 存档**（`data/npcs/<B>/intake/*.md` 至少一份）。目录存在但从未成功对话过 → 拒绝入场，日志 `cast_unavailable:no_intake`；
- `maxCoStars=1`：同一轮出现多个入场名字时，只取第一个，其余记 `cast_overflow` 并忽略；
- `maxCallsPerTurn=1`（省 token 模式）时忽略点名：按单人戏处理，B 只作为在场背景，**不注入“玩家转向 B”**；
- B 与 A 相同名时忽略。

**逐 NPC 共演开关（需求 3.7）**

`data/npcs/<slug>/cast.json = { enabled: false }`，默认关闭。只有 `enabled=true` 且已有 intake 的 NPC
才会被名册解析为“可邀请的配角”；未启用的 NPC **完全不参与共演判定**：

- 玩家在括号里写 `（章籽梦说“……”）` 时，若章籽梦未启用 → 括号只作为 A 的事实/导演指令，**不会拉人**，
  与未开启共演时的行为一致；
- 若章籽梦已启用 → 括号里“名字 + 说话/动作动词”可以被视为邀请（见下）；
- 管理页 NPC 详情提供“允许作为配角参与共演”勾选；关闭时若该 NPC 正在场，下一次请求会把它请出场。

**显式调试指令（需求 3.8）**

玩家消息里的 `/invite XXX`、`/remove XXX` 是**系统指令**，优先于括号解析：

- 支持一行多条，按出现顺序处理；同一名字既 invite 又 remove 时 **remove 生效**；
- 指令文本会从发给模型的玩家消息中**剥离**，只作为调度使用；若剥离后为空，模型看到“（玩家没有开口）”；
- 名字以空白、标点或括号/引号结束：`（/invite 纪澜之）正文` 只取 `纪澜之`，不会把后面的正文一起当名字；
  剥离后残留的空括号（`（）`）一并清理；
- `/invite` 仍受“全局开关 + 该 NPC 已启用 + 有 intake + 名额上限”约束，失败只记日志
  （`cast_command_rejected:<name>:<reason>`），不会改变两人的对话；
- `/remove` 对不在场的 NPC 是 no-op，日志 `cast_command_noop`；
- 入场/离场会作为“本场变化”注入一条极短提示（即使此时没有配角在场），让 A 自然反应；
- 日志记录 `cast.commands` 与剥离前后的玩家文本，便于调试。

**括号内的“邀请”判定（启用共演的 NPC）**

除入场动词（走来/进来/推门/赶来…）外，若括号里出现 **`名字 + 说话类动词`**（说/道/问/答/喊/叫/开口/低声/插话），
也视为邀请。这样 `（章籽梦说“你也在啊”）` 会把已启用的章籽梦拉进场；
未启用的 NPC 不受影响，括号仍是纯事实。

名字匹配来源（按优先级）：

1. `state.rawNames`（游戏下发的全名，含 mod 前缀）；
2. slug 本身；
3. `data/npcs/<slug>/aliases.json`（玩家可编辑的昵称表，如“梦儿”“小弦娘”“弦娘”）；
4. `state.variants`（心境变体）。

> 已知缺口：现有数据里大量昵称（梦儿、小弦娘）不在 `rawNames` 中，因此**建议新增每 NPC 可编辑的 `aliases.json`**，否则点名命中率会明显偏低。

清场条件：

- `sceneKey`（**地点**）发生变化（`sceneKey` 为空时不清场，避免游戏未下发地点时误清）；
- 距 `updatedAt` 超过 `autoExitIdleMs`。**只要本轮结束时有配角在场，`updatedAt` 就会刷新并落盘**——
  它衡量的是“多久没和主角来往”，不是“多久没换人”，否则聊得久一点就会被误判为离场；
  清场原因会记 `cast_stage_cleared:scene|idle`；
- 玩家显式写出离场指令；
- 管理页手工“清空在场”。

### 5.4 认识判定（不建全局名录）

**不做全局名录**。理由：17 个 NPC 的关系以亲属、同门、同铺为主，维护一份跨 NPC 索引需要周期性扫描全部档案、处理改名与 mod 前缀、还要防剧透，成本高于收益；而共演真正需要的信息只有一个——**A 此刻认不认识 B**。

做法：B 确定入场后，在 A 已加载的**当轮 system + 长期记忆**里做一次字符串匹配（B 的 slug / `rawNames` / 别名），得到二值结论，然后改写共演块的一句话：

```
A 认识 B：
  章籽梦你认得（你自己的记忆里提到过她）：镇上杂货铺的老板娘。

A 不认识 B：
  章籽梦这个人你没见过，也没听人提过；她此刻却站在这里。
```

- 判定范围只有 A 自己的数据，**不读 B 的记忆、不读其他 NPC 档案**；
- 每次请求现算，零缓存、零维护、无新文件；
- 昵称命中的准确率取决于别名表（见 §5.3），这也是别名表的价值所在。

### 5.5 A 侧“共演场景”块

位置：记忆之后、提示词之后、格式提醒之前（离玩家本轮最近，优先级最高）。

篇幅预算：300~500 字；B 先说话时追加观测块（+100~200 字），合计 ≤700 字。写作原则：**只陈述现场事实与已发生的公开行为，不下“转述/代答”指令**——A 只是在场者，不是传声筒。

内容要素：

1. 本场为多人场景，列出在场角色及其公开身份；
2. **说话人契约**（`outputStyle=script`）：所有角色（含 A）的台词统一以 `名字：` 开头另起一行；A 的括号动作写在自己那句里；
3. 玩家括号内是**既成事实**与**导演指令**，必须当场承接；
4. 本轮主要对话对象（默认 A；若括号点名 B 则为 B）；
5. A 的合法反应：极短在旁反应（一个动作/半句）、自己也插一句、或不接话；**被点名的是 B 时，A 不复述玩家对 B 说的话**；
6. 长度约束：配角单次 ≤60 字，整段 ≤200 字；回应到点就停；
7. `emotion` / `control` / `intent` 只代表 A，不得把 B 的行为写进 A 的机制字段；
8. 禁止提及“系统/设定/规则/共演”等字样。

**观测块（B 先说话时追加）**：只给 B 的公开输出，不给 B 的设定与记忆。

```
【你刚才看到的】
章籽梦先开了口（她的原话，不是你的口吻）：
章籽梦：「……」
她此刻的神情/动作：……
你看到了这些，但不知道她心里怎么想。
```

草稿（`outputStyle=script`）：

```
【本场现场】
此刻在场的还有章籽梦（镇上杂货铺的老板娘）。她听得见你们说话，也会自己开口。
玩家括号里的动作与场景已经发生，你当场承接；括号里点名谁，谁就是本轮主要回应者。
本轮玩家转向章籽梦说话。你不必替她回答，也不必复述玩家对她说的内容；
你可以只给一个在旁的动作或半句话，也可以自己也插一句，或者不接话。

【写法】
你只写你自己的台词：以「江楚弦：」开头另起一行，动作用括号写在自己那句里。
章籽梦的台词由她本人应答，你不要替她写，也不要给她留“台词位”。
她不替玩家行动，也不替你决定；她不知道你私下的事。
可写 1~3 句，每句不超过 60 字；回应到点就停。
emotion、control 与 intent 只描述你自己（江楚弦）。
```

关键点：**这是"不要替 B 写台词"的显式指令**——主线下 B 的台词由系统插入，A 若也写一份就会重复。

`outputStyle=script` 是默认值。若玩家写“拉到一旁低声说”这类私下交谈，允许 A 只写一句“在柜台后拨算盘，没听清”作为在旁反应（`allowASilence`，默认开）。

### 5.6 配角请求（独立调用，主线）

最小 prompt 预算：

| 组成 | 字数上限 | 来源 |
| --- | --- | --- |
| 公共世界观 | 约 700 | **B 自己的 intake** 中 `## 守住世界观` + `## 通用要求`（与 B 的角色设定同源） |
| B 角色卡 | 500~700 | B 的 intake 中 `## 角色设定/角色背景/角色说话习惯/角色属性` 抽取 + 截断 |
| B 长期记忆 | ≤800（可配） | `data/npcs/<B>/memory.md` |
| 当前场景 + 在场角色 | 约 300 | A 的 `extractGameState` |
| 共享对话 | 约 500 | **本工具自己的公共观测账本**（见 §5.8）+ **本轮玩家发言**，不是游戏 history |
| 演出规则 | 约 350 | 纯文本输出、括号动作 + 台词、允许 `<SILENT>`、禁止赠物/交易/关系声明 |
| 合计 | **约 3.1k 字 ≈ 2.3k tokens** | 输出 ≤300 tokens |

**B 的输出规则**（写进 prompt，并在本地做一次确定性校验）：

- 只输出“括号动作/神态 + 台词”，**台词必须以 `名字：` 开头**；总长不超过 60 字；
- **不得**声称赠出或收下物品、不得宣称关系确立、不得宣称任务完成、不得输出 `{GIFT}`；
- 不得替玩家或 A 行动，不得描述自己看不到的场景；
- 不想开口时输出 `<SILENT>`，此时本轮不插入任何内容（不计入玩家可见文本）。

调用参数：

- `stream: false`，`thinking: { type: "disabled" }`（内部调用，与摘要器一致）；
- `max_tokens: 300`，`timeoutMs: 20000`；
- **B 先跑失败** → 整轮作废（不请求 A、不落盘、向游戏返回错误）；
- **A 已说完、B 接话失败** → A 的回复原样返回，B 本轮不出现；**不得插入“B 没接话”之类的任何叙事**（避免 A 跳戏），日志只在内部记 `costar_failed`；
- 客户端断开时中止 B 的调用（与请求重写一致），不把半截结果写进账本。

**为什么共享对话必须来自本工具账本**：游戏发来的是 A 窗口的 history，其中 B 的台词被包在 A 的 JSON `content` 里，且可能被游戏裁剪。B 的请求需要干净的多说话人记录，因此从 `conversations.jsonl` 的 `segments` 渲染（`[玩家] / [江楚弦] / [章籽梦]`），与游戏 history 解耦。拼装时必须补齐两段尚未入账的内容：**本轮玩家发言**（最后一条 `[玩家]`），以及 **A 先说话时 A 本轮的原话**（`[江楚弦]`，取解析后的 `content`，不是原始 JSON 文本）——否则 B 会答非所问。

> 注意：B 的请求是**完全由 `data/npcs/<B>/` 构造出来的**，不依赖游戏下发的 A 的 system，因此它可以被当成一个普通请求处理（包括请求重写，见 §5.11）。

**台词插入由系统完成**（模型不需要输出占位符）：

- **B 先说话**：B 先跑完 → 把 B 的公开输出写入 A 的观测块 → A 流式时，用流式 JSON 扫描器定位第一个顶层 `"content":"`，在其后插入 B 的**转义台词**；
- **A 先说话**：A 正常流式 → B 跑完后，在 `content` 字符串闭合引号前插入 B 的转义台词（尾部插槽；若 B 未就绪，最多延迟 1 个 delta / 1.5s）；
- 插入前做 JSON 字符串转义（`"`、`\`、换行）；插入后整段仍是合法 JSON，且 `content` 之外的字段（`emotion/control/intent`）逐字不变；
- **槽位定位**：优先按整段 `JSON.parse` 的结果核对，再在原文里定位 `"content"` 字符串值；允许前缀说明、代码围栏、字段乱序，
  并跳过被转义的伪命中（`\"content\"`）；流式仍用增量扫描器。
- **模型没按 JSON 输出**（偶发回纯文本）：不丢 B 的台词，直接把台词拼在正文前/后（head 在前、tail 在后）作为兜底，
  此时游戏端本来也解析不了这轮回复；日志记 `costar_fallback`。仅当 B 自身没有台词时才记 `costar_silent`。

`speakPolicy=addressed` 时，只有以下情况才发配角请求：

- 本轮被点名（含“同时点名”）；
- 本轮新入场；
- 玩家在括号里给了 B 一个动作或台词指令（**已在场的 B 被提及即算**；纯粹提及不会把人拉进场，入场仍只认括号动作 / 点名 / `/invite`）；
- 名字后接 `的`/`家` 等所属描述（`纪澜之的卧房`）不算被提及。

其余轮次只注入 A 侧共演块（约 300 字），不产生配角调用。**不采用“上一轮被点名则本轮继续开口”**：那会让 B 每轮都调用一次，token 成本失控，也不符合“Player 不指定则默认对 A”的规则。

### 5.7 输出契约

`outputStyle=script`（默认，多人场景统一剧本格式，含 A 自己）：

| 场景 | `content` 形态 |
| --- | --- |
| 无人被点名 | `江楚弦：（……）……`，与现状的语气一致，仅多一个名字前缀 |
| B 被点名 | `章籽梦：（……）……` + `江楚弦：（在旁看了一眼）……`（按调用顺序） |
| B 入场 | `章籽梦：（推门进来）……`（入场动作用 B 自己那句的括号承担） + `江楚弦：……` |
| B 离场 | `（章籽梦告辞离开）` + `江楚弦：……`，无 B 台词 |
| 私下交谈 | `江楚弦：（在柜台后拨算盘，没听清那边）`，主体由 B 承担 |

`outputStyle=inherit`（单人场景默认）/`outputStyle=script` 的切换条件：仅当 `multiNpc.enabled` 且本场有配角在场时使用 `script`；其余情况保持现有第一人称写法，保证关闭共演时请求与输出**逐字节一致**。

约束：

- `content` 中不得出现除 `{GIFT}` 之外的占位符；配角台词必须由系统插入，不得要求模型输出任何标记；
- B 的台词不得包含 JSON 结构或代码围栏；
- 换行保持最少（一句台词一行），避免游戏气泡渲染异常。

### 5.8 记忆与落盘（需求 3.6）

**A 侧（默认开启，必须做）**

`conversations.jsonl` 条目新增字段（只追加，不改历史）：

```json
{
  "role": "npc",
  "content": "（章籽梦推门进来）章籽梦：哟，你也在。\n江楚弦：你来得正好。",
  "segments": [
    { "who": "章籽梦", "text": "（章籽梦推门进来）章籽梦：哟，你也在。" },
    { "who": "江楚弦", "text": "江楚弦：你来得正好。" }
  ],
  "coStar": ["章籽梦"],
  "reply_json_ok": true
}
```

`segments` **由插入元数据直接生成**（谁在第几位、插了哪句），不靠事后对 `content` 做正则切分——否则 B 的台词里出现冒号或引号就会切错。

**落盘时机（保证“作废轮不污染记忆”）**

- `stage.json` 先在内存计算，**整轮成功后才写盘**；
- `openNpc(A)`（会更新 A 的 `lastSeen` 并写 state）必须**在 B 成功之后**再调用，避免 B 先跑失败时留下副作用；
- A 的 `conversations.jsonl` 只有在 A 的回复完整结束后才追加；
- **落盘的 `content` 必须是最终展示文本**（A 原文 + 插入的 B 台词），不能直接用上游捕获的 `assistantText`——后者不含注入内容（注入发生在转发层，捕获发生在注入之前）；
- 同理，日志里的 `replyPreview` 与 `reply` 详情也存最终文本。

摘要器改造：

- 有条目带 `segments` 时按说话人渲染 `[玩家] / [江楚弦] / [章籽梦]`；
- **只把 A 的段落计入 A 的言行**，B 的段落标注为“同场他人”；
- A 的记忆里最多留一句“同场：章籽梦”，避免把 B 的行为写进 A 的【赠予往来】【未了之事】；
- 无 `segments` 的旧条目保持现有行为（向后兼容）。

**B 侧（默认关闭）**

开启 `coStarWritesMemory` 时：

- B 的台词由 B 自己生成，归属明确，可直接追加到 B 的 `conversations.jsonl`；
- 条目里必须带**逐句 `speaker`**（`玩家 / 江楚弦 / 章籽梦`）：现有摘要器只按 `role` 推断“玩家 or 本 NPC”，否则 A 的话会被渲染成 B 自己说的；
- 写回时同步 `state.turns += 1`、`lastSeen`，让原有水位/空闲兜底能触发 B 的记忆压缩（`turns` 与直接对话共用，只增不减）；
- 只写 B 在场且有发言的轮次，不写“B 不在场”的轮次，避免 B 的记忆混入与自己无关的场景。

### 5.10 日志（A / B 分开、分色）

同一次请求内的 A、B 调用共享一个 `turnId`。**A 的主日志仍是 `kind:"npc"`**（保留现有筛选与统计口径），只追加 `turnId`、`cast`、`costarSpoke` 字段；B 单独记 `kind:"costar"`：

```json
{
  "kind": "costar",
  "turnId": "t-20261020-0013",
  "actor": "章籽梦",
  "role": "costar",
  "slug": "江楚弦",
  "stage": ["章籽梦"],
  "stageChanged": "enter",
  "addressed": "章籽梦",
  "order": 1,
  "spoke": true,
  "lineChars": 58,
  "tokens": { "total": 2310, "estimated": false },
  "warnings": []
}
```

展示要求：

- **主日志列表**：`actor=主角` 用现有配色，`role=costar` 的条目用**另一种颜色**（左侧色条 + 角色名徽标），并显示 `turnId` 后四位；
- **请求详情**：分两个区块——“主角 A 的请求”“配角 B 的请求”，各自展示完整 messages（标注 `game / memory / prompt / cast / format / player / history / internal`）、思维链、回复、耗时与 tokens；
- 额外展示：调用顺序、观测块全文、台词插入位置（content 开头 / 闭合引号前）、`costar_failed` / `costar_slot_missed` / `costar_deferred` 原因。

沿用 [src/log.js](../src/log.js) 的详情落盘与 14 天保留策略；详情体积上限沿用现有 256KB，超出时优先截断配角区块并标注。

### 5.11 与请求重写的关系（二者共存，不互斥）

请求重写是一个**对 system 模块做删除/改写的预处理器**，它不关心这些模块是游戏下发的还是本工具构造的。B 的请求既然完全由 `data/npcs/<B>/` 构造，就同样可以被重写：

| 对象 | 被重写的模块 | 必须保留 |
| --- | --- | --- |
| A 的请求 | 游戏下发的全部纯文本 system 模块 | `## 输出格式` 里的 JSON 结构（现有规则不变） |
| B 的请求 | B 的世界规则、B 的角色卡（性格/口吻/态度） | **姓名与身份不得改**；长度 30%~150%；非空 |

- **B 的记忆不重写**：记忆是事实层，与外置提示词冲突时由“提示词优先级更高”裁决，改写事实会破坏连续性。
- 一次重写调用同时处理 A 的模块与 B 的模块（用不同的 `<<<SYSTEM id=...>>>` 段），随后按 **重写 → B → A** 的顺序执行。重写不占 `maxCallsPerTurn` 的额度（它只数 NPC 发言调用）。
- B 的模块校验失败时**只回退 B 的模块**，A 的照常生效；日志分别记录。
- 代价：一次重写的输入接近“A 的 system + B 的构造 system”，每轮多一次大调用；页面必须弹窗提示“token 与延迟显著增加”。

## 6. 预算估算

| 场景 | 调用数 | 额外输入 | 额外输出 | 额外延迟 |
| --- | --- | --- | --- | --- |
| 共演关闭 | 1 | 0 | 0 | 0 |
| 共演开启、B 在场但未点名 | 1 | 约 300 字（观测块） | 0 | 0 |
| 只对 A，B 插一句（A→B） | 2（串行） | 约 300 字 + 配角 3.1k 字 | 约 200 字 | A 首字不变，B 台词 +0.6~1.8s 到达 |
| 只对 B（B→A） | 2（串行） | 配角 3.1k 字 + A 侧观测块约 400 字 | 约 200 字 | **首字 +1~2s**（B 先跑完才发 A） |
| 同时对 A、B | 2（串行） | 同上 | 约 300 字 | 同“只对 B” |
| 超出调用预算的反应 | 2 + 延后 | 0 | 0 | 0（挪到下一轮） |
| 再叠加请求重写 | +1 次预处理 | 约 5k~8k 字（A+B 的 system 量级） | 约 5k~8k 字 | **每轮额外 +2~5s**（视模块体量） |

参照：现有单轮请求 11,905 字 / 8,165 tokens。**点名 B 的轮次约 +2.3k tokens；A 单独说话的轮次约 +2.5%；共演关闭时零变化。**

## 7. 风险与缓解（不含已接受的延迟与 token 成本，见 §0）

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| B 的台词显示在 A 的气泡内，可能被 A 的语音朗读 | 体验割裂 | 明确产品预期；台词加名字前缀；限制配角长度 |
| 调用预算耗尽，A 的下半句反应延后 | 反应“慢一轮” | 无需额外注入：上一轮内容已在 history 与账本里；只记 `costar_deferred` 便于统计 |
| A 观测到 B 的台词后模仿 B 的语气 | 串味 | 观测块明确“这是她的原话，不是你的口吻”；A 的 prompt 不含 B 的设定 |
| 括号误判导致角色乱入 | 剧情崩坏 | 只识别“已知名字 + 动作动词”的显式句式；提供手工清场 |
| 任务/话题在场 | 任务判定被干扰 | `skipOnTask` 默认开，**只有真任务/话题轮**（非“闲聊”的任务标题、`本次话题`、`收尾判定`）且配角在场时才退化；普通闲聊即使带 `## 任务：闲聊` 也不退化 |
| A 的记忆被 B 的言行污染 | 长期人设漂移 | `segments` 结构化；摘要器只统计 A 的段落 |
| 多人长文本违背游戏“一两句短句”要求 | 气泡过长、TTS 异常 | 共演块限定配角 ≤60 字、整段 ≤200 字 |
| 关系设定互相矛盾（A 记忆 vs B 卡片） | 前后矛盾 | B 的卡片只作公开事实；冲突时以 A 的记忆为准（A 是主视角） |
| B 的文本声称了游戏未结算的事实（赠物、关系、任务） | 文本与游戏状态不一致 | prompt 明确禁止 + 本地确定性校验（命中则截断该句并记 `costar_claim_dropped`） |
| B 先跑失败导致整轮作废 | 玩家看到一次错误、本轮无回复 | 这是为保证记忆与叙事一致而接受的代价；日志标 `costar_failed`，重试同一句即可 |
| 重写作用于 B 时改坏角色卡 | B 变成另一个人 / 台词跑味 | 只允许改写性格、口吻、态度类句子；姓名与身份做硬校验，不一致即回退原卡 |

## 8. 验证计划

1. **解析回归**：用 `releases/data` 的 840 条真实玩家发言回放，统计入场/离场/点名的误判与漏判（目标：非显式句式误判 0；`章籽梦你来了`、`章籽梦，你怎么看` 这类直呼必须命中）。
2. **开关门禁**：未启用共演的 B，括号里的名字与台词不触发入场、不产生 B 调用；启用后才生效；关闭开关时若 B 在场，下一轮被请出。
3. **显式指令**：`/invite`/`/remove` 单条与多条、remove 优先、未启用/无 intake/超名额拒绝、剥离后为空时模型收到“（玩家没有开口）”。
4. **状态机单测**：入场、离场、点名（括内/正文）、多配角、场景变化清场、超时清场、调用预算与延后、无 intake 拒绝、`maxCoStars` 溢出、`maxCallsPerTurn=1` 时忽略点名。
5. **调用顺序单测**（假上游）：A 先 / B 先 / 同时点名 / A→B / B→A 五种路径的调用顺序、插入位置与最终 JSON 合法性。
6. **插入可靠性**：B 台词含引号、反斜杠、换行、emoji 时的 JSON 转义；**合成 chunk 的字段完整性**；`content` 非首字段时的扫描器行为；尾部插槽超时。
7. **作废语义**：B 先跑失败时，`stage.json`、A 的 `state.json`/`conversations.jsonl`、B 的记忆**都没有变化**（逐文件校验）。
8. **失败叙事**：A 先说完、B 失败时，最终 `content` 与账本里**不含任何“B 未接话 / B 沉默”字样**。
9. **隔离验证**：抓取 A 的请求体，断言其中**没有** B 的角色卡、记忆、`prompt.json`；只有观测块。
10. **文本一致性**：B 声称赠物/关系/任务时被本地规则拦下；`{GIFT}` 出现次数为 0。
11. **存储一致性**：落盘 `content` = 最终展示文本（含注入的 B 台词），不是上游捕获文本；`segments` 与展示文本逐段一致。
12. **前端**：逐 NPC 开关保存后生效；`kind:'costar'` 记录有徽标/筛选/详情，不落到兜底样式；旧日志渲染无变化。
13. **真机对照**：选纪澜之/纪小蝶（母女）与江楚弦/章籽梦（同铺）各跑 10 轮，检查 A 是否“记得 B”、B 是否串味、任务判定是否受影响。
14. **零影响验证**：关闭共演时，请求体与 `0.6.3` 逐字节一致。

| 编排 | 轮内编排（先说话者先跑、最多 2 次发言调用、延后标记） |
| 注入 | A 侧共演观测块（认识/不认识）、注入顺序与来源标注 |
| 输出 | 流式 JSON 扫描器、`content` 开头 / 闭合引号前插入、合成 chunk、失败回退 |
| 记忆 | A 侧 `segments` 落盘与防污染；**B 侧写回（默认关闭，带 `speaker`、同步 `turns`/`lastSeen`）** |
| 重写 | 请求重写覆盖 B 的世界规则与角色卡（姓名/身份硬校验），顺序 重写 → B → A |
| 日志 | `turnId`、A/B 分色、详情两区块、失败/延后/插入失败原因 |
| 前端 | `costar` 徽标、筛选 chip、CSS 配色、详情分支、在场与别名 UI |
| 文档 | [contributing.md](contributing.md) §2 第 8 条补共演作用域的局部缓冲说明 |

交付后可用：开关共演、括号拉人、多人同场、A/B 互相观测、A 侧记忆不串味、**B 可选写记忆**、双开关（共演 + 请求重写）同时生效。

约束：

- 运行时零第三方依赖，`src/` 与 `public/` 只用 `node:*` 与浏览器原生 API；
- 新增定时器（如超时清场）必须 `unref()` 并在 `server.close` 时清除（本方案实际为请求时惰性判断，不新增定时器）；
- 同一 NPC 的落盘与摘要继续走 `KeyedQueue`；
- `conversations.jsonl` 只追加，不改写历史；
- 共演与请求重写**可同时开启**，顺序固定为 **重写 → B → A**；重写覆盖 A 的 system 模块与 B 的世界规则/角色卡（不含 B 的记忆），页面需弹窗提示 token 与延迟显著增加。

## 10. 评审结论（已确认）

| # | 事项 | 结论 |
| --- | --- | --- |
| 1 | 多人场景输出格式 | **`outputStyle=script`**：所有台词带 `名字：`，包括 A 自己 |
| 2 | 入场门禁 | **档案 + 括号显式指令即可入场**；A 不认识 B 时在共演块里如实写明，让 A 自然反应，不做硬拦 |
| 3 | 共演与请求重写 | **不互斥**：重写同时作用于 A 的 system 与 B 的构造请求（世界规则、角色卡），顺序 重写 → B → A；页面弹窗提示成本 |
| 4 | 每轮调用次数 | **最多 2 次 NPC 发言调用**；超出部分延后到下一轮（防止 A/B 互相唤起导致请求无限增长） |
| 5 | 任务/话题轮 | **自动退化单人戏**（`skipOnTask=true`） |
| 6 | 全局世界名录 | **不做**（维护成本高、收益有限），改为 A 侧即时认识判定 |
| 7 | A 静默 / 私下交谈 | **支持**（`allowASilence=true`） |
| 8 | B 失败处理 | **B 先跑失败 → 整轮作废**（不请求 A、不落盘）；A 先说完后 B 失败 → B 缺席，**不写任何“未接话”叙事** |
| 9 | 跨窗口共享舞台 | **不做** |
| 10 | 别名表 | **做**（`aliases.json`），因为昵称不在 `rawNames` 里，点名命中率依赖它 |
| 11 | 逐 NPC 共演开关 | **做**（`cast.json`，默认关）；未启用的 NPC 不参与任何共演判定 |
| 12 | 显式调试指令 | **做** `/invite XXX`、`/remove XXX`，优先于括号，并从模型输入中剥离 |

---

## 11. 明确不做

- 不在**同一次请求**内做“多角色独立气泡 / 独立头像 / 独立语音”——游戏协议一次只接受一条回复。
- 不让配角产出 `emotion/control/intent`，也不让它声称赠物、交易、关系或任务结果。
- 不在默认配置下调用额外模型、不改变现有请求体。
- 不为共演引入新的运行时依赖或后台常驻进程。

### 12.2 “不影响其他模块”的保证

- **关闭共演时零影响**：不读 `stage.json`/`aliases.json`、不发额外请求、不改请求体、不产生 `costar` 日志；`upstream.js` 不启用 transform，仍逐字节直通。验证方式：请求体与 `0.6.3` 逐字节比对（§8.8）。
- **不新增定时器**：超时清场在每次请求时按 `updatedAt` 惰性判断，不需要后台任务，不违反“关窗即退出”。
- **不新增依赖**：`src/cast/*` 只用 `node:*`。
- **不影响单实例 / 端口 / 鉴权 / 数据目录布局**：新增文件都在既有 `data/npcs/<slug>/` 下，`dist.mjs` 的备份恢复按整个数据目录处理，无需改动。
- **不影响摘要与空闲兜底**：A 的记忆仍按原水位；B 的写回只是多了一批带 `speaker` 的条目，旧逻辑可兼容。
- **日志体积可控**：详情仍受 256KB 上限约束；超限时优先截断配角区块并标 `truncated`，主日志只增几个字段。

### 12.3 仍需真机验证（设计已留回退）

1. 游戏能否正确消费**合成 SSE chunk**（`model/id/object/created` 复制、`finish_reason:null`）——若不能，退回“拆分原 delta”的实现。
2. A 的回复是否始终以 `"content"` 为第一个字段——若不是，扫描器按“第一个顶层 content 键”处理；仍失败则按 §3 #2 回退。
3. 游戏气泡对**多行 content + 名字前缀**的渲染与 TTS 朗读表现。
4. 真实 player 文本里“名字在句首”的点名命中率（用 840 条历史回放统计误判/漏判）。
